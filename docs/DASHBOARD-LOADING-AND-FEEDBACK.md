# Faster dashboard loads and clearer action feedback

Research and proposed implementation, 24 November 2026. Scope covers the current local owner dashboard on phones and desktops. Four GPT‑6.2 Sol researchers at medium effort investigated storefronts, waiting behavior, dashboard delivery, and owner actions.

Give unread badges the first implementation slice, as detailed below. Two other changes address the broader loading and repeat-tap issues. Start fetching the selected view’s records as soon as the route is known. At the point where an owner taps Save, Send, or Receive stock, immediately acknowledge the specific action and keep its outcome visible through background refreshes. ShopBot already has thumbnail variants, compressed assets and route splitting. The strongest local evidence points to work starting late and confirmations getting lost.

## Why someone taps twice

A person waiting on a button has two separate questions. Did the dashboard receive the tap? Did the shop record change? A pressed state can answer the first immediately. Only a server result or reconciliation can answer the second. GOV.UK documented duplicate invitations from double-clicks and identifies several causes, including slow feedback and established clicking habits. A UI guard and server-side duplicate protection address different failure modes. [GOV.UK button research](https://design-system.service.gov.uk/components/button/#stop-users-from-accidentally-sending-information-more-than-once)

Four controlled website experiments found that animated loading indicators could shorten perceived waits, with weaker effects in utilitarian or high-involvement tasks. Those findings concern perception. They do not measure ShopBot repeat taps. For a merchant receiving stock, a stable quantity, “Recording 6 pieces…” and a final receipt answer a practical question that motion alone cannot. Use a real count for measurable work such as imports, an indeterminate label for unknown durations, and accessible status text announced without moving focus. [Waiting-time experiments](https://www.mdpi.com/0718-1876/20/4/306) · [W3C status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)

## Implemented in the local checkout

A press now has a visible response, followed by an action label where the user is waiting and a separate result when the server responds. Orders highlights the selected row immediately. Its empty state is tied to the selected stage, query and page. Chat rows reflect known visible unread messages locally and order dots clear when the selected detail is visible. The shop-wide navigation badges still reconcile from the server after a confirmed receipt.

The shell starts the active view’s first read alongside its code. Deep-linked chats start history and inbox reads together. The view reuses that first response even when it finishes before the route code. Loading states keep the navigation available and announce which records are coming. A failed route download has a reload action. Product photos still load after usable rows, and the viewer requests a 640 px preview before the original on zoom for catalog photos.

Chrome DevTools Protocol recorded five cold Products entries per build at 390 × 844, with a disabled cache, 4× CPU throttling, 120 ms network latency, 6 Mb/s download and a 180 ms synthetic API delay. With 50 fixture products, median navigation-to-first-row DOM time fell from **1,098 ms to 912 ms**. The catalog GET moved from a median of 157 ms after its route chunk finished to 121 ms before it finished. Each entry used one catalog GET. These measurements characterize that fixture and do not establish production load times.

Run `npm run build` followed by `node scripts/check-dashboard-feedback.mjs` to replay delayed chats, Orders and product images, a missing route chunk, and an uncertain stock update using synthetic browser data. The full local suite passed 1,177 tests. The p75 budgets and authorized phone acceptance below remain field verification work.

## Implementation order and acceptance

**1. Establish a repeatable baseline.** Build a small browser fixture for a 50-photo catalog, populated order queue and image-heavy conversation. Use an isolated browser profile and synthetic records. Run cold entry, tab switch, Back and warm reload in English and Tamil. Record Chrome/network settings, viewport, device pixel ratio, cache state and API delays. Repeat at least 20 times per comparison under a fixed mobile CPU/network profile. Collect median and p75 for tap-to-acknowledgment, route-to-first-usable-row, first visible photo and action-to-confirmed-result. Include the recorded desktop sequence: switch between chat threads, open Completed from an empty New stage, then visit Products and scroll. For navigation, also capture request count, compressed bytes by type, LCP element and layout shifts. For actions, count repeated activations, POSTs, and committed effects separately. Keep measurements free of message text, identifiers and photos.

**1a. Make the unread badges reflect what the owner just viewed.** This is the first user-visible change. Today the top-level Chats badge counts unread **inbound messages across all conversations**. Each inbox row has its own count. Orders has an unread dot per request and a total on the navigation icon. The “New” stage total continues to include a viewed order until its workflow stage changes. Likewise, “Needs your reply” can remain after reading. Preserve these distinctions in labels and accessible names. [Counts and receipt rules](../apps/server/src/services/owner-reading.ts) · [Chat list](../apps/dashboard/src/RedesignChats.tsx) · [Order stages and unread dots](../apps/dashboard/src/RedesignOrders.tsx)

- **Why Chats lags.** The open, visible timeline records the highest message sequence reached. Scroll events batch the receipt for up to 700 ms. A successful POST emits an event without counts, so the shell requests the summary again. The inbox row receives its count from a separate five-second poll. The thread’s “New messages” divider is set during initial positioning and can outlast the count. When the pill clears, a similar-looking “Needs reply” dot may take its place. Give that persistent workflow indicator a distinct appearance. Jump-to-latest is a separate control driven by scroll position and unloaded pages. [Reading hook](../apps/dashboard/src/owner-chat-reading.ts) · [Inbox and thread](../apps/dashboard/src/RedesignChats.tsx) · [Shell badges](../apps/dashboard/src/RedesignDashboard.tsx)
- **Why Orders lags.** An explicitly selected order detail must be visible. A 500 ms timer then attempts a seen receipt for that exact attention key. The row dot clears on confirmation and the nav count waits for a further GET. Leaving the order before confirmation can suppress the event even if the server saved the receipt. The shell’s ordinary fallback poll runs on a 15-second interval. These are code paths and configured intervals. Actual phone delays still need measurement. [Order receipt effect](../apps/dashboard/src/RedesignOrders.tsx) · [Shell polling](../apps/dashboard/src/RedesignDashboard.tsx)
- **Update at the point of viewing.** Keep one in-document view of pending and confirmed read progress that both nav layouts and list rows consume. Once the owner has opened an order and its detail is visible, clear its dot and subtract its contribution once for that attention key. Keep the server write independent of that paint. In a chat, update as the visible read boundary advances. Subtract only previously unread inbound messages accounted for through that boundary. Sequence numbers also include other traffic, so their numeric difference cannot give a message count. If a jump crosses unloaded history, apply only known contributions locally and get exact counts in the receipt response. Retire the session’s divider once the owner has passed the initial unread range without disturbing scroll position.
- **Reconcile without flicker.** Keep batching chat receipts while scrolling. Have receipts return the accepted key or read-through position and enough authoritative count data to reconcile the affected row and aggregate. Reject out-of-date poll responses and prevent a receipt plus a poll from subtracting the same read twice. Qualifying progress already captured must survive navigation and finish against its original record. In particular, drain the last queued chat position even if the first save completes after switching to another chat. Test the count immediately on returning to the mobile list, where the navigation icons become visible again. An updated order key or message above the captured boundary remains unread. If persistence fails, reconcile with the server, show a quiet sync status, and retry the same receipt while connected. Keep the existing shop scope, monotonic read sequence and independent scrollback anchor. Opening a list, a hidden detail, or an automatic desktop preview alone does not clear unread records. [Receipt endpoints](../apps/server/src/http/owner-reading.ts) · [Existing reading tests](../tests/owner-reading.test.ts)

**Badge acceptance.** Seed 15 unread inbound messages, ten in chat A and five in B. Scroll through four in A. A should show six and the Chats icon eleven. Scroll through the rest of A. A’s badge disappears and the icon shows five. Repeat with a slow receipt, a new inbound arrival, a delayed older poll, scrollback, a jump across unloaded history, a quick switch to B, and a failed receipt. With two unread orders, viewing one removes exactly one dot and one from the Orders icon while the New stage total stays stable. Reopen the same order, then introduce a new revision during the receipt. Exercise mobile bottom navigation and desktop sidebar. Proposed lab target is p75 within 100 ms of qualifying visibility for locally known count changes, independent of an injected two-second network delay. Record authoritative convergence separately and verify the final counts after reload on an authorized phone. The existing viewport/scroll-anchor unit test passed during this audit. The new badge scenarios are planned tests.

**2. Fix action feedback, starting with Orders, compact stock and chat control.** Bind each attempt to the record ID, version, operation and payload at confirmation. Acquire a synchronous in-flight guard and show a specific pending label beside the initiating control on the next paint. Keep the target, quantity and draft visible. Scope any lock to conflicting controls. Track read errors separately from write outcomes. A late response updates the originating record and cannot navigate away from a newer selection. Reuse the existing advanced stock retry pattern and inventory receipt checks. Preserve server-side consent, expected order version, reservations, and outbox rules. Extend the same behavior to settings saves after these paths pass. [Order rules](PRODUCT.md) · [Inventory service](../apps/server/src/services/inventory.ts)

| Outcome | Owner sees | Allowed action |
| --- | --- | --- |
| In flight | “Recording 6 pieces…” at the stock control | Additional taps join or are ignored. Other independent work stays available. |
| Server confirms, refresh fails | “Stock recorded. Couldn’t refresh the list.” | Refresh the read. Keep the receipt visible. |

| Reply accepted into outbox | “Reply queued.” Delivery status updates with the provider result. | Reopen the thread without sending again. |

Keep copy localized in English and Tamil. Use a polite live region for material transitions, preserve keyboard focus, support reduced motion, and keep quiet background polls out of announcements. Prefer a simple pending label for short operations. For import, show processed rows out of the known total when the backend can substantiate it.

Assert one movement/reply/order transition per intent at the database or outbox, no late update to another editor, and no lost draft. An action error survives the next successful poll. Proposed lab budget is p75 at or below 100 ms from activation to the first visible acknowledgment. Record end-to-end completion separately.

**3. Start the active route’s code and first read together.** Move construction of canonical request keys into small functions shared by the shell and views. Keep immediate revalidation where required after a mutation, session change or version mismatch. Load the Settings chunk alongside its snapshot. Parallelize deep-linked chat history only when the conversation and reading-position inputs are known. On return, show same-scope retained rows with an inline updating state; preserve search, selection, scroll and focus. Use a bounded, static row placeholder for an empty first load. **Pass condition.** In a cold trace the selected route’s first GET starts before its chunk finishes, and Settings assets start before its snapshot returns. Each destination issues one initial GET per distinct required key, including the fast-response case. The default inbox still selects the correct conversation and unread boundary. A slow old request never populates the new route. Hold the Completed response after leaving an empty New tab and assert the UI does not show “No orders here” under Completed. Release the response and verify its rows render. Require a reproducible reduction in p75 time to usable rows against step 1, with no regression in warm navigation or Tamil readability.
