# Customer CRUD and conversation UX

Five agents independently investigated the existing customer experience, reproduced defects, and built focused changes. The primary agent integrated the runtime fixes and verified the combined result. Work is tracked in [issue 46](https://github.com/sagomedia/agent-native-whatsapp-bot/issues/46).

| Customer problem | Implemented behavior |
| --- | --- |
| A shared word could select the wrong item, such as a pipe cutter for “remove wire cutter.” | Edit target validation rejects conflicting product heads and explicit qualifiers, including a model-proposed row ID. Ambiguous targets still need a customer choice. |
| A successful edit could be followed only by an item count. | Existing-cart changes receive a brief factual acknowledgement, naming actual added, removed or changed rows. Counts, requested measured amounts and continuous lengths stay distinct. Read-only turns, rolled-back writes and new empty-cart creation do not receive this extra acknowledgement. |
| An agent question could hide the related-product warning, while an empty search falsely claimed a saved request or repeated known details. | Valid clarification questions stay first above photos; related suggestions retain an explicit warning. Empty searches only claim a saved item when a draft line exists. Known dimensions are not re-asked as the same dimension; a known length still allows a missing diameter question. Detailed no-match requests retain their supplied description and count with correction/shop-check next steps. |
| WhatsApp action titles could become identical after clipping, causing a failed product reply. | Plain, image and carousel buttons receive distinct short titles when needed. The original action IDs and events are retained. |
| A price check or cart review could erase an unfinished removal choice without changing the cart. | An unresolved cart goal survives read-only interruptions while the draft/version remains unchanged. Typed answers and existing choices resume it. Actual cart changes still invalidate stale choices; “yes” and product approval do not execute a deferred removal. |

New tests cover English, Tamil and Tanglish feedback, measured and unknown amounts, actual WhatsApp payloads, edit rollback, product identity conflicts, no-match honesty, dimension-specific clarification and nine interruption/recovery journeys. Existing compound-removal expectations now include the factual removal acknowledgement. The five-item transcript changes only two text fields for factual edit feedback; all cards, actions, quantities and stages remain identical.

Final combined verification passed: `npm run build` (including TypeScript), all **804 integration tests**, and all **4 Python catalog-cleanup tests**. Hosted checks and immutable deployment identifiers are recorded in issue 46 and the pull request. Tests use synthetic inputs and disposable PostgreSQL schemas. Deployment must preserve merchant products, original photos, store settings, environment and untouched customer carts, and take a fresh restorable backup. No historical customer commands or customer test messages are executed. Fresh phone/speaker acceptance remains open for the user's review after deployment.
