# Public WhatsApp customers and owner review

Set `WHATSAPP_AUDIENCE=public` to accept every valid WhatsApp customer number on the configured business account and phone. The default remains `test`, with the existing one-to-five-recipient pilot list. Keep the pilot list in the private environment as a rollback aid; it does not restrict public mode. App signatures, business account, phone identity, shop scope, owner authentication, AI budgets and the 24-hour reply window still apply. Public inbound access does not authorize marketing or remove template requirements for later outbound notifications.

Public receive, delivery statuses, typing indicators, owner replies, order notices and automatic sends use the same audience rule. No phone verification or proof of purchase is required to start a conversation. Greetings and thanks use the existing deterministic replies. Voice notes can be the first message. Spelling mistakes, Tamil/Tanglish and unknown product names are not spam rules.

Each unique provider message is committed to the inbox before admission decisions. A durable conversation guard uses server receipt time, not the customer's timestamp. The initial burst limit is 30 messages in a two-minute window. An identical normalized text is answered once; its second occurrence in the same shopping context is saved quietly, and its third occurrence hands over. Greeting variants share one repetition key. A repeated quantity after a different product/state binding remains actionable. Identical attachment bytes are decoded and retained but are not repeatedly sent to AI; the second copy is held quietly, and the third hands over. Original voice bytes remain subject to the existing size/download/decode limits.

Semantic classification reuses the normal interpreter result. It makes no additional classifier request. Two consecutive completed non-shopping interpretations, or genuinely unreadable speech results, hand over. A meaningful shopping clarification, product lookup, quantity question or pending order is not counted simply because it has not added a cart line. Provider outages/quota errors are not evidence of customer spam. Interpretation is imperfect: the result is owner review, never a permanent customer ban.

Handover sets the existing owner mode and assistance flag, records a reason in the owner audit, invalidates in-flight leases and retires queued assistant replies. It sends at most one plain acknowledgement per owner-control revision. Messages, order drafts, requests, attachments and cost records remain available. An already-started model call may still incur its normal charge, but its stale result cannot change the order or send a reply. Later messages remain in the owner's inbox without AI interpretation. Bounded attachment download/decoding can continue for owner playback; no transcription/model call runs in owner mode.

The owner reads the full retained history and replies through the protected dashboard. Returning control to the assistant resets the admission counters on the next inbound message. Held old messages are not replayed as shopping commands, so the owner should address any real item requests in that history before resuming. This avoids duplicate cart changes or an automatic spending backlog after a flood.

Schema 46 adds an independent guard table. It does not change inventory, payments, existing orders or budget caps. The public privacy page describes the actual enabled AI/media features, owner review and existing retention: records remain until operator deletion, including the stated backup limitations. No automatic retention/deletion service is introduced.

## Verification and rollout

Run the PostgreSQL integration suite, build/typecheck and catalog checks before packaging. The admission regressions use synthetic customers and fully mocked model/Meta transports: new unlisted senders and delivery receipts; duplicate webhook retries; repeated text across restarts; a 50-message flood with another customer unaffected; unrelated versus typo/unknown-product input; first-message voice; owner replies/resume; in-flight result invalidation; and attachment preservation without repeated inference.

Build a verified immutable release against the active source and unchanged dependency lock. Use the existing backup/staging/upgrade tooling. Save the private pre-change environment, set public audience, activate and verify readiness, bound app/number IDs, non-paused controls and schema 46. Keep the previous compatible release and pilot recipients. A real message from a second phone remains the final device-level check; synthetic test results do not prove delivery to an actual new customer.
